# Retake v0.0.1: the implementation plan

Status: **built, not yet released** (2026-11-02): all 34 commits have landed, with the changes
since noted where they are, and the release's publishing (33) and the open checks below remain.
Planned 2026-10-26. The contract is written ([README](../../README.md), [Documentation/cli.md](../cli.md)) and the
[proofs of concept](2026-10-26-proofs-of-concept.md) behind it are done. This record is the plan for building it, as a series of
commits on the `initial-implementation` branch, the first of which adds the command line.

**The README and Documentation/cli.md define what Retake does, and every commit conforms to them.**
This plan doesn't restate them: it says in what order they're built, what each step has to prove,
how it's tested, and how Puzz moves over. Where the plan and the contract seem to differ, the
contract wins, and the plan is corrected.

## Puzz, Retake's first user

[Puzz Kids](https://apps.apple.com/us/app/puzz-kids/id6749132459) ([puzz.kids](https://puzz.kids)) is an iPhone and iPad app of puzzle games and read-aloud books for
children. Its App Store previews were made by a pipeline built in its own repository, and Retake is
that pipeline extracted into a tool for any app. Puzz is the first app to use Retake, so switching
its previews over to Retake is v0.0.1's final check.

Retake is generic. Puzz is named here, in the plan for Retake's first version, because that check is
part of the plan; it isn't named in Retake's code, its comments, or its other documentation, and
shouldn't be.

## Goal

v0.0.1 is everything the [README](../../README.md) and [Documentation/cli.md](../cli.md) describe, working as they describe it,
released. Every command does what its section says, every field of every file is read and acted on,
and anything the docs promise that isn't built by the end is taken out of them rather than left as a
stub. A check the project's owner decides the release doesn't need is marked **Below the bar for
v0.0.1** where it stands, saying why, rather than removed. It's done when:

1. **Every documented command and field works**, to the contract, with tests, and with what needs a
   device shown on one.
2. **Puzz's previews are made with it.** Puzz's three videos are recorded and cut by Retake, for
   iPhone and iPad, from scenes, sets and edits in Retake's format, replacing the tooling Puzz grew
   for them (`Scripts/PreviewVideo/`: `take.sh` and its recorder, `edit.sh` and its editor,
   `derive-ipad-edit.py`, and `Scripts/launch-heist.sh`), with none of it left in the path.
3. **v0.0.1 is released**, as the README's Install section says: a signed, notarized `retake` on
   GitHub Releases, installed with `mise`, carrying TheInsideJob and Retake's support library.
4. **The repository shows how to use it**: an example app in `Examples/`, with its own
   `retake.json`, sets, scenes and edits, and an integration test that takes it from install to a
   cut video, as a model for a project of one's own.

## How the work is cut

Each step is one commit, small enough to review on its own and complete on its own terms: it builds,
its tests pass, and what it adds works, even when nothing uses it yet. A step that needs a device to
prove it is tested on one, and what it showed is noted against its check below, in the same commit.
A commit that grows too big to review is split rather than squeezed.

- **The docs are the contract.** A command whose commit hasn't landed yet fails saying so, on the
  branch; none does in v0.0.1. A change to what a command does goes into `Documentation/cli.md` or
  the README on `main` first, as its own commit, and the branch follows it; the branch carries code
  and tests.
- **Everything added is tested**; see [Testing](#testing).
- **The checks are worked off as the commits land.** Each group of commits below lists what it has
  to prove beyond its unit tests, most of it on a device. A commit ticks the checks in its area,
  noting what each showed, or moves one to [After v0.0.1](#after-v001) when the release doesn't need it. By the
  release, no check is left open.
- **Ported code is reshaped, not copied.** Puzz's recorder and editor, and the spikes, are the
  starting point for much of what follows. Each is moved to Retake's file formats and its anchors,
  rather than carried over with its old shape and adapted later.

**The example app (2).** A small SwiftUI app, a notes app like the README's examples, with buttons,
typing, a sheet that arrives late, a drag and a screen that turns: everything a scene can drive, and
nothing tied to any one app. It replaces the spikes' sample app as what each device check runs
against, and its `retake.json`, sets, scenes and edits grow with the commits that read and use them,
so they're always an example that works. Its Xcode project is checked in, so it builds with Xcode
alone; signing comes from a local, untracked setting naming the developer's team.

**Reading the project (3–8).** Swift types for `retake.json`, sets, scenes and edits, read strictly:
a key Retake doesn't know is an error, and every error names the file and the path to the field

path. Each field's description, range and default is written once, on its type, since the schemas
(31) and the reference (32) are generated from them. Sets resolve `extends` without cycles; scenes
check their step ids, give their steps a hold from `defaultHold` when they don't give their own, and
add nothing to their set's launch, which is all of it; edits hold anchors and per-device overrides,
and still read a time given in plain seconds. `validate` gets every check a schema can't make that
needs no takes; the ones that need takes come with anchors (24).

**Recording (17–23).** Launching on a set: staging its files with `devicectl device copy to`, the
launch environment, the launch check, and the cleanup launch when a run ends. Steps go through
`ButtonHeist.withSession`, one plan per step, as `spikes/client071` drives the app; an `orientation`

writes a scene a step at a time on the device, each action given with named options, asked for at a
terminal and named when missing from a pipe, with JSON replies, so a person, a script or an agent
can drive it; its `inspect` action prints the screen, and adds nothing to the scene. `takes`,
`discard` and `clean` read and delete what `record` writes; `doctor` runs, in order, checks the
commits before it already make.

## Testing

Every commit tests what it adds, enough to trust that it works and to catch it breaking later. The
tests are for behaviour that could be wrong, not for code that can't be:

- **What's worth a test.** The contract: what each command does, its errors and exit statuses.
  Reading files: every rule a field has, and the message and path for each way of breaking it. The
  logic Retake owns: anchors and their arithmetic, choosing a device, `extends`, per-device
  overrides, conforming an edit, the editor's timing (where each clip, caption and sound lands on
  the video's clock), and metadata written and read back. And every bug fixed, with a test that
  failed before the fix.
- **What isn't.** Restating a constant, a property returning what it was given, or what a library
  already guarantees, such as ArgumentParser parsing a flag. A test that couldn't fail for a real
  mistake isn't written.
- **Unit tests are fast and need no device.** None takes more than a second, and the suite runs
  under a time limit of seconds, so a test that hangs is found at once. What talks to the outside —
  `devicectl`, `codesign`, The Button Heist, AVFoundation's capture — sits behind a small seam, so
  the logic around it is tested against recorded output: `devicectl`'s JSON captured from real
  devices, a step log from a real take. The editor is tested by rendering short compositions from
  small generated movies and checking frames and times, not by eye.
- **Devices are tested on devices.** What only a device can show is checked on one when it lands,
  and noted against its check in this plan. The example's integration test (34) repeats the whole
  path on a device, and is opt-in: it runs when a device is named for it (`RETAKE_DEVICE`), and is
  skipped otherwise, so `swift test` never needs one. Its parts that need no device, `validate` on
  the example project and `cut` from a small take checked in for it, run every time.

The entries are grouped by how much rides on them, and within each group kept in the order they
came up. Those a later change made moot are gathered at the end, each ending with **Obviated:**
and why.

### Most consequential

Choices a project's files, commands or takes come to depend on, or that rest on something not yet
checked; changing one later breaks someone, or a wrong guess shows in every video.

- **How a set lies over the set it extends** (5). The README says only that `extends` "builds on
  another set". As built: `files`, `defaults` and `environment` merge by key, the extending set's
  value replacing the base's; `aspect` merges by device type; `state` is the nearest set's that
  gives one, else `clean`; and `arguments` add up, the base's first, so a set can't take back an
  argument its base passes. A default whose value is an object replaces the base's whole, rather
  than merging into it. The README could say this in a sentence. **Decided:** with the project's
  owner on 2026-11-06, kept as built: `arguments` add up, an object default replaces the base's
  whole, and a set can't remove what its base gives (`null` stays an error), each of which can be
  loosened later without breaking a set; `appearance`, which came later, is the nearest set's, as
  `state` is. The README and the set reference are to say so. `aspect` gives way to a boolean,
  `previewAspect`, which shapes the window as the App Store preview for the device type, turned in
  landscape, and is the nearest set's that gives one: no project shaped portrait and landscape
  apart, nor the iPhone at all, and a landscape preview is the portrait one turned.
- **`occurrence` counts from 1** (6), like an anchor's step numbers, though The Button Heist's own
  ordinal, which it becomes, counts from 0. It's the field a person writes when two buttons share a
  label, so it reads as "the second Delete". **Decided:** with the project's owner on 2026-11-06,
  `occurrence` keeps its name and counts from 1, as an anchor's step numbers do, and the README,
  `Documentation/cli.md` and the schemas say so of both; they steer to an element named closely
  enough to be the only match, by its traits, identifier, value or hint, with `occurrence` a last
  resort that breaks when the layout changes, and to anchoring on a step's `id` rather than its
  number; and `compose` suggests, for a tap at a point and for each element `inspect` lists, the
  shortest name that picks the element out, giving an `occurrence` only when nothing else tells it
  apart.
- **Edit fields the README describes without naming** (7). The clip's longer sound cross-fade is
  `audioCrossfade`, as in Puzz's edits, beside `takeAudio`; it can't be shorter than `crossfade`. A
  still is `{ "take", "at" }`, a frame of another take, and stills pop in one after another from the
  clip's start, as Puzz's do, with no timing of their own yet. A spotlight's `padding` is 8 points
  and its ring white unless given; a blur's `radius` is 20. **Decided:** with the project's owner on
  2026-11-06, `audioCrossfade` fades both sides: the clip before's take sound fades out over it, and
  the clip's own starts that much before the clip before ends, ahead of its picture, and fades in
  over the same stretch, while the picture cross-fades over `crossfade`. A clip's `stillsIn` is an
  anchor for when its first still pops in, the rest following as before, and the stills otherwise
  pop in as before. A blur's `radius` is in screen points, scaled to the canvas as its rectangle is,
  as every other size in an edit is, and defaults to 9, which on a 6.1-inch iPhone's canvas is about
  the old 20 canvas pixels. A still's `{ "take", "at" }` is kept, `take` naming a scene as a clip's
  does, and so are a spotlight's `padding` of 8 and white ring.
- **An anchor's `edge` is `"start"` or `"end"`** (7): the edge of the step an `offset` or `fraction`
  counts from, overriding the README's default of forward from the end and back from the start. The
  README's "`edge` counts from the step's other edge instead" reads as a flag; a named edge says the
  same thing without a reader having to work out which edge is "other". **Decided:** with the
  project's owner on 2026-11-06, an anchor has one reference point, the step's start unless `edge`
  says `"end"`, and a signed `offset` counts from it, forward when positive and back when negative,
  0 being the point itself; `edge` alone is that edge, and `"start"` stays valid as the default said
  out loud. A `fraction` is a share of the way from the reference point to the neighbouring step,
  forward to the next step's start or back to the previous step's end, which is what an explicit
  `edge` already did; a share of the step's own length was the other reading, but it can't say the
  example's "halfway from the title typed to Synced showing", and it would leave no mechanical
  migration. Before, the sign picked the edge, so `offset: 0` was the step's end while no offset was
  its start; now a consumer can predict an anchor from one rule. `cut` writes a time in seconds as a
  plain offset from the step's start. The example's edits were migrated by giving `"edge": "end"` to
  each anchor with an offset or fraction of 0 or more and no `edge`, and the owner's own projects'
  edits must be migrated the same way, since such anchors otherwise move silently, an offset back by
  its step's length.
- **An `orientation` step ends when the screen's elements have moved and then held still** (18). The
  README says the step "ends when the app has turned", so the next step's points land on the turned
  layout. `devicectl device orientation set` returns in about 0.2 s, before the app has relaid out;
  The Button Heist's `WaitFor(.screenChanged)` doesn't fire for a rotation (proof of concept 4); and
  neither its public client nor `devicectl` gives the screen's size (asks record, 10). So Retake
  reads the screen every 0.1 s until the elements' frames differ from before the turn and are the
  same twice running, and fails after 5 s, asking whether the app supports that orientation. A turn
  to the way the device already faces doesn't wait. It could be fooled by a screen whose elements
  don't move when it turns (a single full-screen element, say), which would end the step at the 5 s
  timeout, failed. The alternative without The Button Heist is the support library reporting its
  window's size, which needs a contract change and a file copy mid-take.
- **Drags at other than 0.5 s go through The Button Heist's tooling SPI** (18). 0.7.1 refuses a drag
  with a `duration` inside a plan, the public client's only way to send it ("drag duration … is not
  a durable heist action"); only the tooling SPI's direct commands take one. The contract keeps
  `duration`, and real scenes need it (one app's drags are 0.25 s and 0.8 s), so a drag at exactly
  0.5 s goes in a plan, and any other is sent with `@_spi(ButtonHeistTooling)`'s `admit`/`execute`,
  confined to `ButtonHeistDriver.perform`. Decided with the project's owner on 2026-10-27: use the
  SPI for now, and record what The Button Heist would have to make public to drop it (asks record,
  8–10). The other choices were dropping `duration` from the contract, or playing every drag at 0.5
  s with a warning until upstream changes.
- **A turned take is stored as a camera fixed to the device would see it** (20). A movie has one
  size, the first frame's, so frames of the other shape are turned a quarter to fit: frames from a
  device turned `landscape-left` a quarter clockwise, `landscape-right` a quarter anticlockwise, so
  the app's top is along the device's top edge as it was held. Each change of shape is logged with
  its time and turn (`TakeWriter.ShapeChange`), so the edit can turn them back either way
  (`letterboxed`, upright; or `device`, as stored). Which way is right rests on `devicectl`'s
  `landscapeLeft` meaning the device's top turned to the left, as `UIDeviceOrientation` names it
  (its help says it sets the "simulated device physical orientation"): the frames themselves can't
  show which way the device physically faced. One look at the iPad while it's turned left would
  confirm it: its front camera should be on the left. If it's the other way, the two turns swap, in
  `TakeWriter.turn(for:startedFacing:)`.
- **The step log's shape** (21). It's Retake's own JSON, defined in `TakeLog`, until the reference
  (32) documents it: the take's scene, number, set and state; the device, app and versions; when it
  was recorded and, for a failed take, `failure`; the movie's `duration` and `size`; for a take
  recorded from before launch, `launch` (`launched`, `reported`, `connected`); the clock's
  `deviceAhead`; each step's `number`, `id`, `action`, `start`, `end`, `timedBy` (`device` or
  `mac`), `touch` and `touchEnd` for a tap by point and a drag, and `elements` after it; and the
  movie's `shapes`. Times are seconds into the movie, to the millisecond, and points to the
  hundredth. A `waitFor`'s element arriving is its `end`, rather than a field of its own; the
  README's "when a waitFor's element appeared" reads as that.
- **`rehearse` became `record --dry-run`** (21b), as the project's owner asked in review: the
  contract changed on `main` first (`Fold rehearse into record, as --dry-run`). A dry run chooses
  scenes as `record` does, so with none named it plays only scenes with no take yet, unless
  `--force`; naming the scene is the usual way to try one out. `--from` needs `--dry-run` and one
  scene named, since a take that skipped steps' holds isn't one to keep.
- **`compose` replaced `inspect`, and the `inspect` step went with it** (21c), as the project's
  owner asked in review: the contract changed on `main` first (`Replace inspect with compose, for
  writing a scene on the device`). The 19 entries about `inspect` and `--watch`, under Obviated, describe what it
  was; its settling after launch lives on in `compose`, which shows the screen once two readings
  agree. A scene file with an `inspect` step now fails to read, as an unknown key.
- **A project lives in `Retake/`, its folders inside it lowercase** (review of 2026-10-27; contract
  on `main`, `Keep a project in Retake/…`). The project's owner asked for a `Retake` folder holding
  everything, `retake.json` included. As built: `Retake/retake.json`, with `sets/`, `scenes/`,
  `edits/` and `output/` beside it, all lowercase like `retake.json`, so paths read the same as
  before inside the folder, while the top folder, which sits among the repository's own, is
  capitalised as an app's repository's folders usually are. The output directory, `RetakeOutput/`
  when it sat beside the app's files, is plain `output/` inside `Retake/`. Capitalising the inner
  folders too (`Sets/`, `Scenes/`, `Edits/`, `Output/`), as some iOS repositories lay out theirs, is
  the alternative, at the cost of every path in the docs changing again.
- **Device aliases, and `install`'s builds, live in `~/Library/Caches/retake/`** (review of
  2026-10-27, reversing two choices the same day; contract on `main`, `Keep builds and device
  aliases in ~/Library/Caches/retake, not the project`). Aliases went from `~/.config/retake/` into
  the project, gitignored, when the owner asked that nothing be written outside the repository (not
  into `retake.json`, which is shared, since aliases hold a device's UDID and its owner's name).
  Then each `install` rewrote thousands of files in `output/build/`, which Claude Code lists after
  every command that changes them, so builds moved to the cache, a folder per project
  (`builds/<parent>-<folder>-<hash of its path>/`), and the owner asked for aliases to go with them,
  so what Retake keeps for itself is in one place. Aliases are each person's, for every project. The
  cost: clearing `~/Library/Caches` forgets them (`devices add` names each again), and makes the
  next `install` a full build. The output directory keeps `installed.json`, the bundle ID `install`
  last embedded, for "Finding the app", so a new output directory still has to be installed into, or
  name `bundleID`, as before.
- **`discard` folds into `clean --takes`, and `videos/` becomes `cuts/`** (review of 2026-10-27).
  The owner asked for `clean --takes <scene>@<take>` and `--cuts <edit>`, which leave `discard` with
  nothing of its own, so it's gone. `discard` refused to delete a take an edit pins; `clean` instead
  names those takes when it asks, since deleting later takes is now how an edit goes back to an
  earlier one (`conform` always pins the latest). Rendered videos moved from
  `output/videos/<type>/<video>/` to `output/cuts/<type>/<edit>/`, to match the flag and the
  command. A deleted take's number is used again by the next take, as numbering is one past the last
  on disk.
- **Matching elements by trait or hint** (asked 2026-10-27, in review; decided the same day: both,
  contract on `main`, `Name an element by its hint and traits too`). An element can be named by its
  `hint`, exactly, and by its `traits`, a list of The Button Heist's trait names, every one of which
  it must have; a name The Button Heist doesn't know is an error where it's read, so a misspelling
  doesn't quietly match nothing. `compose` takes `--hint` and `--traits header,selected`, and when
  an element is missing asks only for a label, value or identifier, the usual ways to name one.
  Elements on screen, and in step logs, carry their hint.
- **How anchors resolve** (24). `TakeTimeline` resolves an anchor to seconds into its take, and an
  element to its frame, for `cut`, `conform` and `validate` alike. A step's place is its log entry's
  start and end, its neighbours' end and start bounding the gaps either side, with the take's start
  (0) and end (its duration) standing in past the first and last steps; `start` and `end` are steps
  of no length at those two moments. `edge` picks which of the step's edges an offset or a fraction
  counts from, the direction still the sign's. A fraction of 0 is the edge itself, and counting back
  from `start` or forward from `end` is the only "fraction with no step on that side". A resolved
  moment outside the take, or a clip whose `to` isn't after its `from`, is a problem too.
- **The schemas are written beside the readers, not derived from them** (31). Each file type's
  schema is a Swift value in `Schemas/FileSchemas.swift`, field for field with its reader, and the
  readers stay hand-written, since their messages and cross-field checks are what the schemas can't
  carry. What keeps the two together is tests: the checked-in schemas must be what the types
  generate; the example project's files must fit and read; and on a corpus of 47 files, right and
  wrong in each way a field can be, schema and reader must agree. Deriving the readers from the
  schemas is the alternative, a rewrite of every reader for one source of truth. Writing the corpus
  found a reader bug: a clip or step that couldn't be read was dropped from the list, so the checks
  by index (cross-fades, caption targets, ids) named the wrong one. Fixed in its own commit.
- **The release is a script and a workflow, signed only where the Developer ID is** (33, in part).
  `Scripts/release.sh <dir>` refuses `RETAKE_BUTTONHEIST_PATH` and any Xcode but `.xcode-version`'s,
  builds `retake` optimised for arm64, and packs `bin/retake` and `share/retake/` (the framework,
  the support library, the licence) at the tarball's root, as `retake-<version>-macos-arm64.tar.gz`
  with its SHA-256. With `RETAKE_RELEASE_IDENTITY` it signs with the hardened runtime, and with
  `RETAKE_NOTARY_PROFILE` too it has it notarized. `.github/workflows/release.yml` runs it on a
  `v<version>` tag, from secrets, and publishes with `gh release`. Checked locally, unsigned: the
  tarball unpacked elsewhere found its `share/retake/`, and `doctor` launched the example on the
  iPad from it. Not yet checked, waiting on the certificate: signing, notarization, the workflow
  itself (and whether GitHub's runners have Xcode 27.2), `mise` installing it, and the camera
  prompt.
- **A turn settles despite a looping animation** (2026-10-27). Puzz's book has a bobbing page-turn
  arrow, an element whose frame changes on every look, so "the same twice running" never came, and
  the step failed after 5 s though the app had turned (its take's shapes show the change at 31.62
  s). Polling showed the layout settling in four looks and only that arrow moving after. Now a look
  has settled when nothing moved since the last, or only a third of the elements at most, all of
  which were moving the look before too; and something other than those must have moved since before
  the turn, so an animation alone doesn't pass for a turn. Turned this way, the take recorded, its
  turn settling in 1.1 s.

### Worth a look

Behaviour a person writing scenes or running Retake would notice, or an open risk, each cheap to
change before v0.0.1 and costlier after.

- **`null` for an optional key is an error, not the key left out** (3). `"speed": null` fails with
  "expected a number, found null", since no field means anything by `null`, and a strict reading
  that rejects unknown keys should reject a value that says nothing as well. Treating `null` as
  absent would be friendlier to generated files.
- **Notes and warnings go to standard error, prefixed `note:` and `warning:`** (4), so that output
  meant for a pipe, or `--json`, stays clean; errors keep their `✖`.
- **A set's defaults reach the app as JSON in the launch environment** (12), `RETAKE_DEFAULTS`,
  rather than a file staged in the container: they're JSON values already, and copying a file to the
  device costs a second a launch. A set with a very large `defaults` might need the file.
- **`clean` keeps launch arguments and the global domain** (12): the in-memory defaults still read
  `-key value` arguments, as a set's `arguments` may give, and global settings such as
  `AppleLanguages`, which the spike's store dropped; only the app's own domain starts empty.
- **An unsigned app gets the minimal development entitlements** (14): given `--identity` and
  `--profile`, `embed` signs an app built with signing off with the profile's app ID for its bundle
  ID, its team, `get-task-allow`, and its own keychain group, as the spikes did, not every
  entitlement the profile allows. An app that needs capabilities should be built signed, for `embed`
  to keep its own.
- **Each staged file is its own `devicectl` copy** (17), about a second each, so a set with many
  files launches slowly. Copying a folder is one copy; a set could be staged as one archive the
  support library unpacks, at the cost of another contract change.
- **Client errors are classified from `FenceError`'s public cases** (18). The Button Heist's own
  mapping from an error to its failure code is internal or SPI (asks record, 9), so
  `ButtonHeistDriver.classify` reads `.diagnostic`'s code, and maps `.authFailed`, `.notConnected`,
  `.actionTimeout` and `.sessionLocked` itself. A mismatch is 3 with "embed it again"; a refused
  token is 3; an unreachable server is retried for 10 s, then 3; a connection lost during a step is
  3; anything else in a step is 1. A new error case in a later release would fall through to 1 with
  its description.
- **A `waitFor` over 60 seconds fails only when it plays** (18). The Button Heist refuses a wait
  longer than its maximum, 60 s unless `BUTTONHEIST_MAX_WAIT_TIMEOUT` raises it, but scenes accept
  any positive `timeout`, so a 600 s wait reads and validates, then fails at its step. `validate` or
  the scene reader could check it against the maximum, or the schema give it a maximum of 60.
- **A take's lead-in is from the movie's first frame** (21), so the first step starts `leadIn`
  seconds in. A take recorded from before launch waited no more, until Puzz's takes showed why it
  should (2026-10-27): its lead-in now starts once the app is reachable. `duration` runs a little
  past the last step's end plus `tail`, by the time stopping takes.
- **A failed take doesn't count as a take when choosing scenes** (21b). Documentation/cli.md says
  `record` alone records "every scene with no take yet"; a failed take can't be pinned, so a scene
  whose takes all failed is recorded again, as take 2 after a failed 1. Takes are numbered after the
  last on disk, failed or not, and never renumbered.
- **How `compose`'s actions are written** (21c). Each line is an action's name and `--name value`
  options, with `--gone` the one flag; a point is `<x>,<y>` (`--from 120,590`); double quotes keep
  spaces, and `\n`, `\t`, `\"` and `\\` inside them stand for what they do in JSON, so `--text
  "Groceries\n"` types a return. `help` takes an action's name bare (`help tap`), as a person would
  type it. One spec per action (`ComposeActionSpec`) gives parsing, `help`'s text and what a
  terminal asks for, so they can't drift apart. An element is asked for as its label, then its
  value, then its identifier, whichever is answered first.
- **A scene `compose` writes is reformatted** (21c): its fields keep their order and values, but the
  file is rewritten as Retake writes files, with its steps a line each, so a hand-written file's own
  spacing and line breaks don't survive the first step added. A new file gets `$schema` and `set`;
  `--set` for a scene that already names one is a misuse (2), and for one that leaves it to
  `defaultSet`, it's used for the session but not written into the file.
- **`compose --json` replies a line each** (21c): `{"ok": true, "screen": […]}` after launching and
  for `inspect`; `{"ok": true, "number": n, "step": {…}, "screen": […]}` for a step added; `{"ok":
  true, "number": n, "step": {…}}` for `set` (`hold` and `id` until the review of 2026-10-27);
  `{"ok": true, "steps": […]}` for `steps` and after a replay; `{"ok": true, "help": "…"}`; and
  `{"ok": false, "error": "…"}`. Steps are written as the scene file writes them, elements as the
  step log does. Notes and warnings go to standard error, so standard output is only JSON.
- **Commands find `retake.json` in the current directory before `Retake/retake.json`** (review of
  2026-10-27), so a project is found from the repository's root and from inside its own folder, and
  a project kept beside the app's files, as before, still works. With both present, the nearer wins;
  `init` won't make one inside the other.
- **`clean`'s `--takes` and `--cuts` take a value or none** (22). ArgumentParser can't parse an
  option whose value may be left out, so `Retake.run` passes a bare `--takes` or `--cuts` on as
  `--takes=*`, and `*` means every one; a value is a comma-separated list, as Documentation/cli.md
  writes it. The alternatives were flags with the names as arguments, which can't say which names
  are scenes and which edits, or `--all-takes`.
- **`compose`'s step actions are named as scenes name steps** (review of 2026-10-27). The owner
  found the README's steps and Documentation/cli.md's actions didn't match: `compose` had `wait`,
  `turn` and `pause` for a scene's `waitFor`, `orientation` and a step that's only a `hold`. They're
  now `waitFor`, `orientation` and `hold`, so what's learned in one carries to the other. That left
  `compose`'s own `hold` (the last step's hold) clashing, so it and `id` became one action, `set
  --hold <seconds> --id <name>`, either or both. `waitFor` is the one camel-cased action, as the
  file spells it; `orientation` keeps `--to`, since actions take only named options.
- **An element is found in the latest reading at or before the moment** (24), as the README says:
  the screen read after the latest step to end then, to the millisecond. Before the first step has
  ended there's no reading, so an element can't be named there: a spotlight on what's on screen from
  the very start of a take has to start after its first step, or use a `rect`. A spotlight's or
  blur's element is looked for at its `from`, or its clip's `from`, not again later on; an element
  that moves meanwhile is better as a `rect`, as the README says.
- **`validate` warns about takes it can't check, and fails only on those it can** (24). Takes aren't
  in a repository, so a fresh clone, or CI, has none: an edit that pins no take of a scene, or pins
  one that isn't recorded here, or failed, is a warning that what's cut from it isn't checked. An
  anchor or element that doesn't resolve in a take that's here is a problem. A step id the scene
  lacks is reported once, by the check that needs no take. Checked on the example: a copy of its
  edit pinned to the iPad's takes of this morning validated, and one with an offset past the take's
  end, an unknown step, and a blur on an element not yet on screen failed, naming each.
- **Framing a turned stretch** (26). Upright, the window is the portrait shape at the top of the
  frame, or the landscape one at its left, as the take's `aspect` recorded; without one, the whole
  frame. `letterboxed` fills the canvas with an upright portrait window and fits a landscape one
  whole, centred between bands; `device` crops the window where it lies in the stored frame and
  fills the canvas with it. A take that starts turned, whose file is landscape, is framed the same
  way, though with `device` its landscape file overflows the portrait canvas, which no scene does
  yet.
- **The export is two passes** (28), as in the editor Retake grew from: Core Animation layers render
  only through an export session, which can't set a bit rate, so the first pass writes a ProRes
  master (`AVAssetExportPresetAppleProRes422LPCM`) with the overlays and the sound, keeping a
  sped-up take's pitch (`.spectral`), and the second re-encodes it frame by frame to H.264 High
  Profile 4.0 at 11 Mbps with 256 kbps stereo AAC at 48 kHz, drawing the blurs as it goes: each
  turn's over the whole canvas, swelling to a sigma of 18 at the turn and back, and each the edit
  names over its rectangle at its `radius`. App Store Connect takes ProRes 422 HQ, so the master is
  for keeping and re-encoding rather than uploading.
- **`cut`, end to end** (28). `Cutter` reads the edit and each take it pins, fails before rendering
  on a take not pinned, not recorded, or failed, on takes from devices with different screens (by
  the screen's points, or for takes from before 27, their capture's size), and, unless a draft, on a
  length outside App Store Connect's 15 to 30 s; then plans, composes, places the overlays, grabs
  the stills, lays the sound in and exports. A draft only warns about its length, since drafts are
  for timing, and is written as `<edit>-<type>-draft.mp4`, so it's never taken for the one to
  upload. An `.mp4` over 500 MB fails after it's written. Checked on the example: a copy of its edit
  pinned to the iPad's takes cut as a draft in 2.7 s, warning it was 9.2 s long; in full, it failed
  on its length; slowed to 20.3 s, it cut in 7.6 s to a ProRes master and an `.mp4` that `ffprobe`
  reads as H.264 High, level 4.0, 1200×1600 at 30 frames a second, with a silent stereo AAC track at
  48 kHz, its captions drawn as the edit places them, the iPad's own `y` among them, and the 3:4
  window filling the canvas.
- **The `.mp4`'s bit rate is a target, not a floor** (28): 11 Mbps is asked of the encoder, as the
  pipeline Retake grew from did, but a mostly still screen comes out lower (the example's 2.5 Mbps).
  App Store Connect's 10–12 Mbps is a "target bit rate"; that pipeline's videos were accepted at
  what the encoder gave, so it isn't forced up. When Puzz's videos are uploaded (see the release
  checks), that's the test.
- **A time in seconds shared by every device type** (29) is turned into an anchor against the first
  device type in `devices` whose old take is here; one in a device type's override, against that
  type's. Seconds were only ever written against one take, so for an edit that already cuts both
  types from seconds, the other type's moments may move; per-type overrides hold any that must
  differ.
- **`status` judges a video out of date by what it was cut from** (30): its edit's file modified
  since the video was written, the takes in the video's own record no longer the ones the edit pins,
  or a pinned take's step log written since (a take recorded again under its number, after a
  `clean`). File times can say a video is out of date when it isn't (an edit saved unchanged); a
  hash of the edit and takes in the movie's record would be exact, and is the alternative if that
  proves noisy. A pin's newer take is the latest that didn't fail. Device types with no scene, edit
  or video aren't listed.
- **`info --json` and `status --json` have shapes of their own** (30), not yet in
  Documentation/cli.md: `info` prints a list of `{"movie", "take"}` or `{"movie", "video"}`, a video
  as the `.mp4`'s description holds it and a take with its step log's names (`scene`, `take`, `app`,
  `device`, `buttonHeist`, …); `status` prints a list of `{"type", "scenes", "edits", "videos"}`.
  The generated reference (32) is where they're written down, with the other commands' JSON.
- **`retake` is signed with the camera and microphone entitlements** (33), which the hardened
  runtime needs for macOS to ask for either: recording a device's screen asks for the camera, and
  its sound for the microphone. Not yet checked: which a signed, `mise`-installed `retake` is asked
  for, and who the prompt names.
- **`record` keeps a launch's console log in a temporary folder** (34, follow-up): the support library's crash on iOS 17
  was found in it, under `$TMPDIR/retake-<scene>-…`, which nothing says. A failed take could name
  its log, or keep it beside the take.
- **An ambiguous match lists the elements without their traits** (34, follow-up): the two "Library"
  elements were listed identically, and the step log had to be read to find one was a header. The
  message could give each element's traits, the thing that tells them apart.
- **This iPad's connection drops now and then** (34): on "Sam's iPad", `devicectl`'s connection was
  invalidated mid-take twice in five, failing the take with "No route to host", and once the screen
  sent no frames. The next try went through each time. Whether that's this device, its cable or iOS
  17's CoreDevice tunnel isn't known; Retake marks the take failed and says to retry, which is
  right, but a take could be retried once on a dropped connection, as a launch is.
- **Retake never adds `"$schema"`** (asked 2026-10-27, reversing 3's choice): `init`'s `retake.json`
  and `compose`'s new scenes no longer name their schema, and the example's files dropped theirs.
  Every file is read against this Retake's schema anyway, so the key is only for editors, and a
  project adds it where it wants completion. `conform` still brings a `"$schema"` naming one of
  Retake's schemas up to this Retake's, and leaves any other URL, such as a project's local copy, as
  it is.
- **A recorded launch's lead-in starts once the app is reachable** (2026-10-27, reversing 21).
  Puzz's `rewards-book` and `subscribe` record their launch, and on `ipad` their first tap came 0.26
  s after the app connected, while its profile picker was still sliding in, so it missed, and every
  point tap after it was one step behind. Puzz's own tool, which Retake came from, waited `leadIn`
  after connecting, and those scenes were written to it (first tap at 3.63 s against 2.55 s now).
  The device test now checks that the first step comes `leadIn` after `connected`, and fails on the
  old behaviour (seen to). A take of a recorded launch is now about `leadIn` longer.

### Minor

Internal choices, details, and problems found and fixed along the way; recorded so the reasoning
isn't lost, with nothing to decide unless one comes up again.

- **Lists in error paths count from 0, steps in anchors from 1** (3). An error's path follows JSON
  tools and editors, so the third step is `steps[2]`, while an anchor's `step` numbers steps from 1,
  so the same step is `{ "step": 3 }`. Documentation/cli.md's example,
  `scenes/ipad/create-note.json: steps[2]: unknown key "tapp"`, reads either way. The alternative is
  counting paths from 1 to match anchors, at the cost of differing from every JSON tool.
- **A `"$schema"` that isn't one of Retake's URLs is accepted without a word** (3), on the view that
  a project may point editors at a local copy; only one of Retake's own URLs naming another version,
  or another kind of file, warns.
- **Values may nest 100 deep** (3). The parser stops there with an error rather than recursing
  further: no Retake file nests more than about ten deep, and Swift Testing's threads overflowed
  at 500.
- **`init` without a terminal leaves `build` out rather than failing** (4). When the directory's
  Xcode project has several schemes and no one can be asked, `init` still creates the project,
  without `build`, and notes which schemes there were; `install` then needs `--scheme` or `--app`
  until `build` is added. Failing instead would make a script give `--scheme` up front.
- **`init` names a workspace only when xcodebuild couldn't tell** (4): a workspace beside its
  project, as CocoaPods leaves, is written as `"workspace"`; a lone project or workspace isn't
  written at all, since `xcodebuild` finds it. It looks only in the current directory, not in
  folders below it. Since the project moved to `Retake/` (review of 2026-10-27), `xcodebuild` runs
  in a folder with no Xcode project of its own, so a project created anywhere but beside its Xcode
  project names it, relative to the project: `"xcodeproj": "../MyApp.xcodeproj"`.
- **A set can't set `DYLD_*`, `INSIDEJOB_*` or `RETAKE_*` in its `environment`** (5), since Retake
  launches the app with its own; a set naming one fails. It could instead be allowed with a warning,
  for someone deliberately overriding Retake's choice.
- **A `files` entry's trailing `/` must match on both sides** (5): a destination ending in `/` is a
  folder, copied from a source folder ending in `/`, and a mismatch is an error rather than a guess.
  Destinations can't start with `/` or contain `..`; sources are relative to `retake.json` and may
  use `..` for fixtures shared with another project.
- **A scene's `set` defaults to `defaultSet`** (6), so the README's "a scene names its set" became
  "names it, or the project's `defaultSet`"; `validate` reports a scene with neither (8).
- **Steps can't be held on the setup list with ids** (6): setup isn't recorded, so an id there would
  name a moment no take has. Holds are allowed in setup, to let the app settle before recording.
- **Volumes have no upper limit** (7): `volume` and `takeAudioVolume` must be 0 or more, so a quiet
  effect can be raised above its file's level; 1 is the file as it is.
- **`validate` checks anchors against scenes without takes** (8). Documentation/cli.md lists anchors
  resolving among the checks that need takes; an anchor's step id existing in its scene, or its
  number being in range, needs only the scene, so `--offline` checks that too, as the README's "an
  anchor's step id existing in its scene" suggests. Resolving the moments themselves still needs
  takes (24).
- **Validating named files reports only their own problems** (8). A scene named on its own is
  checked against its set, but a problem inside that set isn't reported unless the set is named too.
- **Retake waits out macOS releasing a device's screen** (10). A process asking for a device's
  screen within about 8 seconds of another releasing it is never offered it, so Retake records when
  it releases the screens and waits out the rest before asking again, up to 8 seconds; see the
  Devices checks. The wait isn't announced, since it's short; a note could say why a command paused.
- **`devices` lists connected devices only** (10): an unavailable or disconnected device isn't
  listed, though an alias for one is, marked not connected. A device on the network is listed,
  saying it can't be recorded.
- **A build from a clone learns its clone's path and commit from the framework's build** (11).
  SwiftPM's manifest can't run git or write files, so `Package.swift` only marks a build from a
  clone (`RETAKE_BUTTONHEIST_CLONE`), and `retake version` reads the path and commit
  `Scripts/fetch-insidejob.sh` recorded when it built the clone's framework. Building Retake from a
  clone without running the script shows the clone as unknown. A build-tool plugin could stamp them
  into the binary instead.
- **A local Retake finds TheInsideJob in `~/Library/Caches/retake/insidejob/`** (11), which
  `Scripts/fetch-insidejob.sh` fills, rather than downloading it on first use: the README's
  building-from-source steps run the script, and a command that needs the framework and finds none
  says to. Downloading on first use would save a step.
- **The take's staged files are consumed once copied** (12): the support library deletes
  `tmp/RetakeSet/` after laying it out, since nothing on the Mac can delete files in the container,
  and a take whose set has no files would otherwise get the last take's.
- **The launch report is a file copied back** (13), rather than something read through The Button
  Heist: a hidden accessibility element wasn't visible to it (proof of concept 4), and its status
  carries nothing of Retake's. The copy costs about a second a launch, once a take.
- **`embed` names the identity it used by its certificate's SHA-1** (14), which is what it reads
  from the app's signature, and what `--json` reports.
- **`install` builds for the device by its id** (16), `-destination id=<UDID>`, rather than for any
  iOS device, so Xcode's signing includes the device, and a build that can't be is caught before
  embedding. The embedded copy goes in `RetakeOutput/build/installed/`, replaced each time, which is
  where "Finding the app" reads the bundle ID from.
- **A take's launch stays attached to the app's console** (17), `devicectl … launch --console`,
  logged to `RetakeOutput/logs/<take>.log`: the attached launch holds the device connection for the
  take and keeps the app's output for when a launch fails, whose last lines the error quotes.
- **The Button Heist's port and token are new for each launch** (17), a random port from 20000 to
  60000 and a random token, so a stale app from an earlier take can't be driven by mistake. A port
  already taken on the device fails the launch check rather than being retried.
- **`clean --on-device` waits up to 6 seconds for iOS to reopen the app**, then closes it (17).
  Without the wait, the app closed straight after the cleanup launch is opened again by iOS and left
  running.
- **A launch whose app is never reached is tried once more** (18). The README promises "a launch
  that doesn't take is tried again", and proof of concept 3 saw a first connection fail once and
  then work. Connecting is retried for 10 s; if the app still can't be reached before any step has
  played, the app is launched again, once, with a note. A failure after the first step has played
  isn't retried, since the app's state has moved on.
- **The cleanup launch runs after a failed rehearsal too** (18), so a failed step leaves no take's
  copy of the app's data on the device. If the cleanup itself then fails, the step's failure is
  what's reported, with a warning to run `retake clean --on-device`. A `live` set has no take copy,
  so it gets no cleanup launch, as `record`'s "when any take was clean or cloned" says.
- **A `waitFor` that runs out is reported in Retake's words** (18): `"Done" was still on screen
  after 4 s.` The Button Heist's own text for it names its predicate
  (`elementsChanged(exists(target(predicate(value="Title"))))`), which says less. Other failures
  pass The Button Heist's message through as it is, which for a missing element is several lines
  listing what was on screen, useful for fixing the step.
- **A step's run is given its longest wait plus 60 seconds** (18) as The Button Heist's timeout for
  the plan, so the wait's own timeout is what ends it, not the plan's.
- **`rehearse` prints each step once it has played, with its wall time** (18), nothing while it
  runs: a 10 s `waitFor` is silent until it's done. Printing a step as it starts would show what's
  being waited on, at the cost of two lines a step, or a line rewritten in place.
- **Device tests run one at a time, all of them** (19). Each device suite was serialized only within
  itself, so with a third suite they ran side by side on the one device, and one suite's launch
  ended another's (`The app didn't start with Retake's support library`, a staged file missing).
  They're now nested in one serialized `OnDevice` suite, in `LaunchingTests.swift`; a new device
  suite goes in an `extension OnDevice`.
- **A take that starts turned keeps a landscape file** (20): its later upright frames are turned
  back the other way. A turn the recorder isn't told of, such as one by hand, is turned a quarter
  clockwise, the more usual way. Frames of the file's own shape are never turned, so a device turned
  straight from one landscape to the other, or upside down, is stored as it came, upside down
  relative to the device; `device` turns would show it so. No scene step does that yet.
- **The device's rotation animation is recorded as it comes** (20). Between the stream's two shapes,
  the device sends its own rotation, and for a frame or two content of the new layout in the old
  shape; the recorder stores them as they are. The edit's `turnBlur` is what hides them.
- **Recording counts as started once half a second is written** (20), and a writer that fails before
  then is started over, up to three times, as the recorder Retake's was built from found it does now
  and then (-12737). No frames in 15 seconds is an environment problem (3). A frame the encoder
  isn't ready for is dropped and counted, as a live capture must; the unit tests make the writer
  wait instead (`TakeWriter(live: false)`), since frames made up in a tight loop would otherwise be
  dropped by however busy the machine is.
- **The recorder finds the screen by the alias's capture identity, then by the device's name** (20),
  since `Device` doesn't carry the capture identity; `record` (21) passes the alias's when the
  device was named by one.
- **Commit 21 is two commits** (21). The step log and movie metadata are one, recording a take in
  Retake's core with no command; `retake record`, choosing scenes, numbering takes, keeping failed
  ones and summarising, is the second. Together they're the table's 21.
- **Steps are timed by the device, kept within the round trip** (21). The device's times can't be
  before the step was sent or after its reply, so an offset measured slightly off is clamped to
  those. A step without the device's times (a turn, a hold, an `inspect`) is placed from when the
  Mac sent it and heard back, and says so with `"timedBy": "mac"`.
- **The launch marks are when Retake did each thing** (21): `launched` when `devicectl` was asked to
  launch, `reported` when the support library's report was read back, which is polled every half
  second and copied over, so up to about a second after the library wrote it, and `connected` when
  The Button Heist's session began. An edit cutting in on the launch screen should cut from the
  frames, between `launched` and `reported`. A launch tried a second time records both, and the
  marks are the second's.
- **A take recorded from before launch shows the home screen first** (21), with the device's own
  apps on it, until the app opens. The edit cuts in after; the take keeps it.
- **Movies say when recording started, and nothing about failure** (21). The metadata is written as
  the movie starts, so `com.apple.quicktime.creationdate` is the take's start, and a failed take's
  movie doesn't say it failed; its step log does. `com.apple.quicktime.model` is the device's
  marketing name, `retake.device.model` its identifier.
- **One cleanup launch per run** (21b), after the last scene, as Documentation/cli.md says, rather
  than one per take, which would add about four seconds a scene: each launch deletes earlier takes'
  copies anyway. A run that ends on an environment problem (the app can't be reached, say) stops
  there, and still cleans up.
- **The device's screen is found by its alias's capture identity**, else by its name (21b): a device
  named by UDID or name, with no alias, is looked up among the capture devices by name, waiting up
  to ten seconds for it.
- **`record` prints each scene, each step and a summary** (21b): `Recording create-note, take 3, on
  <device>.`, its set and state, each step once played with its wall time, then a line a scene: `✓
  create-note: take 3, 13.6 s, in RetakeOutput/takes/ipad/create-note/3.mov`, or `✖` with why,
  saying when the failed take was kept. Scenes not reached after `--stop-on-failure` are listed. It
  exits with the worst status among the scenes.
- **`compose` doesn't wait out holds** (21c): steps run one after another as they're given, and the
  scene's steps replay without holds (the setup's too). Changed in review (2026-10-27): a replay,
  after launching, `undo` or `replay`, waits out each step's hold, as a take does, since a step can
  need the app to have settled after the one before; a step given now still runs at once. A replay
  that fails says so and composing carries on from wherever the app got to, so the step that broke
  can be undone.
- **What's on screen after a step is read again** (21c), rather than taken from the step's evidence,
  so it's the same reading `inspect` gives; one extra reading a step, which composing can afford.
- **Control-C ends `compose` as `quit` does** (21c), so the device is still cleaned up.
- **An element that matches several is explained in a scene's terms** (21c). The Button Heist fails
  such a step, as the README now says, with "N elements match … use ordinal 0–(N−1) to select one",
  or past ten matches "10+ elements match … use ordinal 0, 1, 2, ... to select one", counting from
  0; a step's `occurrence` counts from 1, so Retake rewrites it: how many match, to name the element
  more closely by its traits, identifier, value or hint as well, or as a last resort to give
  `occurrence`, from 1 to N, followed by The Button Heist's list of the matches. Recognised by the wording of its message
  (`Player.ambiguity`), tested against that wording; not seen on the device, where the example has
  no two elements The Button Heist counts as the same.
- **Ending `devicectl` can't hang any more** (21c). A device run hung for 50 minutes in
  `LaunchedApp.stop()`: it had asked the attached `devicectl … launch --console` to end, and
  `Process.waitUntilExit()` never returned, though `devicectl` had ended. Detaching now waits for
  the process's termination handler, at most five seconds, then ends it with `SIGKILL` if it's still
  running, so a run can't be held up by it (commit 17's code, fixed here since it held up this
  commit's tests). A hung run had also held the device, so the next run's tests waited behind it.
- **`init --config` suggests `mise.toml`, not a wrapper script** (review of 2026-10-27). The
  project's owner suggested a small `Retake` script that sets `RETAKE_CONFIG`. Retake is installed
  with `mise`, whose `[env]` sets variables for every command run anywhere in the repository, with
  `{{config_root}}` for the repository's root, so `init` prints those lines instead; a script would
  be one more file to keep, and only works when it's what's run. `init --output-dir` needs neither:
  it's written into `retake.json` as `output`, relative to the project when the directory is in the
  same tree as the current directory, and as given when it isn't (`/Volumes/Scratch/retake`).
- **`init` offers to name the devices connected, then asks for others** (review of 2026-10-27). It
  asks once for each iPhone or iPad connected by USB that has no alias, at a terminal only,
  suggesting its type (`ipad`, then `ipad2`), which Enter takes, and `-` skips. Then, as the owner
  asked, it asks whether there's another device to name, and if so watches for one to be connected
  by USB, for up to a minute, offers to name it, and asks again until the answer is no. A device it
  has offered once isn't offered again, named or skipped. A failure naming one, such as its screen
  not being offered, warns and carries on: `devices add` can name it later.
- **`init` refuses to make a project where commands already find one** (review of 2026-10-27). Found
  trying it: run inside `Retake/`, `init` made `Retake/Retake/`. With no file named, it now fails
  (2) when the current directory has `retake.json` or `Retake/retake.json`.
- **An edit's `tapSound` also plays as a drag's finger comes down** (review of 2026-10-27). The
  owner asked whether drags play it. Touches are drawn for drags as well as taps by point, and the
  editor this one is reshaped from played the sound at every drawn touch, drags included, which that
  app's previews rely on; so it plays at each drag's start too, and the README says so. The name
  stays `tapSound`, for the finger landing.
- **`inspect` with an element matches as The Button Heist does** (21c, review of 2026-10-27): each
  of `--label`, `--value` and `--identifier` given must equal the element's exactly, and
  `--occurrence` isn't taken, since the list it prints is what `--occurrence` counts. Matching with
  The Button Heist's own predicates, rather than Retake's, would need a round trip to the app.
- **Why an `orientation` step can't wait on The Button Heist** (asked 2026-10-27, in review). The
  owner asked whether the app posts `screenChanged` or `layoutChanged` when it turns, and whether
  that needs app code. The Button Heist's `screenChanged` isn't the notification alone: it's its own
  judgement that the screen was replaced, from a `screenChanged` the app or UIKit posts, or inferred
  from a modal, tab, navigation title, header or the tree's shape changing (`ScreenClassifier`). A
  turn keeps the same screen, so it's rightly not a screen change, and UIKit doesn't post
  `screenChanged` for one, since VoiceOver would then move focus; apps shouldn't add it. Whether
  UIKit posts `layoutChanged` on a turn isn't known, and doesn't help yet: 0.7.1's public waits
  can't name it (`NotificationPredicate` matches an announcement's text or element, not its kind).
  So the asks record's 10, the screen's size or a turn through the public client, stands.
- **Unit tests run with `TMPDIR` on the external drive** (2026-10-27). The Mac kernel panicked
  during a run: `DeviceNaming.suggestedName` first built its candidates as `[type] + (2...).lazy
  .map { … }`, and `+` with an array copies the whole sequence, an infinite one here, so the test
  grew memory until the disk filled with swap. It's a loop now, tested. The suite's run under its
  usual time cap, with `TMPDIR=/Volumes/Data/tmp/retake-tests/`, since the internal disk has little
  room.
- **`clean` without a terminal needs `--yes`** (22): it lists what it would delete, then fails (2)
  saying to give `--yes`, rather than deleting unasked. A scene, take or edit named with nothing to
  delete is misuse (2), so a typo deletes nothing.
- **A step log records frames and frames dropped** (22), which `takes` lists. They're new to the
  log, so a log written before has neither, and `takes` leaves them out for it rather than saying 0.
  The log is now read back strictly, as every file Retake reads is (`TakeLog.read`), which anchors
  (24) build on.
- **A take whose step log can't be read is listed, and counts as failed** (22), with what's wrong: a
  missing movie or log, or a log that isn't one. No edit can pin it, and `clean` deletes it.
- **What `doctor` checks, and how** (23). Xcode's tools by `xcode-select -p` and `xcrun --find`. The
  device as commands choose it, then that it's paired and its screen is offered for capture, by the
  alias's capture identity or the device's name, waiting up to 10 s, as recording does. Signing by
  `security find-identity -v -p codesigning` and the profiles in Xcode's and MobileDevice's folders:
  a development profile covering the bundle ID (exactly or by wildcard), the device, not expired,
  and for a certificate in the keychain, matched by SHA-1, since an identity's name in parentheses
  isn't always its team; the most specific app ID wins, then the latest expiry. The app by
  `devicectl device info apps`. The launch on the project's `defaultSet`, or an empty `clean` set,
  through the same path `record` launches by, so it checks what a take would. Signing only warns
  when the bundle ID is unknown, while the app check fails (2), as other commands do then.
- **Building Retake outside the repository** (2026-10-27). SwiftPM's `.build/` is in the repository,
  so every `swift build` changes thousands of files there, which Claude Code lists after each
  command. Builds and tests now use `--scratch-path /Volumes/Data/Caches/retake-swiftpm`; the old
  `.build/` is left as it is.
- **A take records its `aspect` in its step log** (25), the set's shapes for portrait and landscape
  as they were when it was recorded, since the set may change afterwards, and the editor crops to
  the window that shape gave the app, at the top of the frame. A take recorded before has none, and
  is framed as though the app filled the screen, so takes from before 25 that used `aspect` should
  be recorded again. Sets now give `previewAspect` instead, and the log keeps the shapes it resolves
  to, so takes recorded with `aspect` still cut.
- **The editor's first part is three pieces** (25): `CutPlan`, where each clip's stretch of its take
  falls on the video's clock, at its speed, overlapping the clip before by its cross-fade;
  `ClipFraming`, the app's window in a frame, scaled to fill the preview's canvas and cropped evenly
  on whichever axis overflows (a hair of each side on an iPhone, nothing on an iPad at 3:4); and
  `EditComposition`, both laid out in AVFoundation on two alternating tracks. The first two are
  pure, tested on their numbers; the composition is tested by reading frames of a composition of two
  small generated movies, before, during and after a cross-fade. A cross-fade longer than either
  clip it joins fails the cut, naming the clip.
- **A turn's blur is placed by the cut, and drawn by the export** (26). Blurring needs every frame
  drawn again, which the export does (28), as the pipeline Retake grew from did; `EditComposition`
  works out when each blur falls, `turnBlur` seconds centred on the moment the frames change shape,
  kept within its clip, for the export to draw.
- **A take records its screen's size in points** (27), read from `devicectl device info displays`
  (the primary display's native size over its point scale, portrait) before the app launches, so the
  editor can find the log's points in the frames: a capture isn't the screen's pixels (the iPad's is
  a 1200×1718 stream of a 1668×2388 screen), and neither The Button Heist's public client nor the
  support library's launch report says the screen's size. On the iPad, `create-note`'s take 2
  recorded 834×1194, with its `aspect` and 825 frames, none dropped. A take recorded before has
  none, so touches, spotlights and blurs can't be placed in it, and it needs recording again.
- **What's drawn over the picture is planned, then drawn** (27). `Overlays` places each caption,
  touch, spotlight, blur and still on the video's clock and its canvas, from the edit, the cut plan
  and the takes' logs, and is tested on its numbers; `OverlayLayers` draws them as Core Animation
  layers, reshaped from the editor Retake grew from, with its sizes, colours and animations:
  captions in 54-point heavy rounded type on a pill of their colour on both canvases, a 92-point dot
  for each touch, a dimmed canvas and pulsing ring for a spotlight, stills popping in a grid. Core
  Animation renders only through an export, so the drawing is looked at once the export lands (28);
  until then a test checks the layers' order and a caption's place.
- **Screen points reach the canvas through each framing** (27): the capture's pixels per point (its
  width over the screen's, upright), then the frame's turn, then the framing's crop and scale, so a
  touch or a spotlight lands on the same thing in a turned and letterboxed stretch as upright. A
  take that didn't record its screen's size (before 27) can't have touches, spotlights or blurs
  placed, and the cut fails saying to record it again.
- **Blurs are placed by the cut and drawn by the export** (27), like turns' blurs, since blurring
  draws every frame again; a blur's `radius` is its strength, in canvas pixels, as the export will
  use it.
- **A still is cropped as its clip's footage is** (27), with the clip's first framing, so it has the
  canvas's shape; the export grabs each still's frame from its take, and hands the frames to the
  drawing.
- **App Store Connect's preview specifications, checked** (28, 2026-10-27, on its "App preview
  specifications" page): 886×1920 for iPhones with Face ID or Dynamic Island (the iPhone Duo among
  them), 1200×1600 for 11- and 13-inch iPads; H.264 up to High Profile Level 4.0 at 10–12 Mbps, or
  ProRes 422 HQ; at most 30 frames a second; 15 to 30 seconds, and at most 500 MB; stereo AAC at 256
  kbps, 44.1 or 48 kHz. `PreviewSpec`'s sizes stand. Older iPhones' sizes (1080×1920, 750×1334) and
  the 9.7-inch iPad's (900×1200) aren't types Retake records, so aren't offered.
- **The sound, planned then laid in** (28). `SoundPlan` places each effect at its anchor, which must
  fall within what its clip plays, the tap sound at each touch drawn, the takes' own sound under
  their clips, and the music; `EditComposition.add` lays them into the composition as the editor
  Retake grew from did: music on its own track, fading out over its `fadeOut` at the end, and
  failing the cut when shorter than the video; takes' sound alternating between two tracks with
  their pictures, at their clips' speeds, fading in over a clip's cross-fade and out over the next
  clip's `audioCrossfade`, or its cross-fade; and effects each on the first track free when it
  starts, cut short and faded over 0.2 s when given a `duration`. A take's sound plays at its clip's
  speed, as the README says, its pitch kept by the export.
- **The take writer's test mode can't hang** (28). Writing a movie not live, as tests do, waited for
  the writer to take each frame, but a writer with a sound input stops taking video once it's far
  enough ahead of its sound, so a test writing 60 frames and no sound waited forever. It now gives
  up after 2 s and counts the frame dropped, and the editor's tests write their movies with a
  picture-only writer.
- **A draft is the same two passes, faster and smaller** (28): an H.264 first pass instead of
  ProRes, then the preview at half the size and a lower bit rate, the master not kept, blurs drawn
  all the same, since a draft gets shared.
- **A video's metadata** (28): the master carries Documentation/cli.md's QuickTime fields, and the
  `.mp4` the software and the whole record as JSON in its description, as the contract says; each
  list (app versions, devices, Button Heists) holds each distinct entry once, in the order the video
  first shows it.
- **A video with no sound gets a silent sound track** (28), stereo AAC at 48 kHz, since App Store
  Connect's audio requirements describe a stereo track and nothing says it may be left out.
- **`conform` lays an edit out as a person would** (29): `JSONWriter.fitting` puts an object or list
  on one line when it fits in 100 columns where it starts, and lays it out otherwise, which is how
  the example's edits are written, so a rewrite's diff is only what changed. Only `conform` writes
  this way; `init`'s `retake.json` and `compose`'s scenes keep their own layouts. Making every file
  Retake writes use it is the alternative, which would change how `retake.json` looks after `init`.
- **`conform` checks the new takes as `validate` does, and anything it would warn of fails it too**
  (29): every anchor inside its take and in order, everything in a clip within what the clip plays,
  every spotlight's and blur's element on screen; nothing is written unless all of it holds.
- **A video's master records the app's bundle ID** (30, contract), as its `.mp4` did, so `info`
  reads the same record from either. Masters cut before this lack it, and `info` leaves it out.
- **What the schemas leave to the readers** (31): ids unique and not number-like; setup steps
  without ids; `edge` only with an offset or fraction; the first clip not cross-fading; a caption's
  `clip` being a later one; a set's file and folder paths inside the app's data and the project, and
  matching in ending with `/`; `null` nested inside `defaults`. Each is a message from `validate`
  and every command that reads the file, so an editor accepts a little that Retake doesn't.
- **Every object in an edit takes overrides, in the schema** (31): each is a definition, and its
  `iphone` and `ipad` keys refer to a partial copy, with every key optional all the way down, lists
  whole. That's anchors and elements too, since the reader lays an override over any object, so
  `"ipad": { "to": { "offset": 0.4 } }` moves only an anchor's offset. The top's overrides leave out
  `devices`, `takes`, `intent` and `$schema`. Inline copies, the first try, made the edit's schema
  119 KB; as definitions it's 44 KB.
- **The checked-in schemas are at `Documentation/reference/<kind>.schema.json`** (31), beside the
  reference that 32 generates, and name this version's URL as their `$id`; the release (33)
  publishes them at that URL.
- **The reference is regenerated by its test** (32): `RETAKE_REGENERATE=1 swift test --filter
  Reference` rewrites `Documentation/reference/<kind>.md`, and without it the test fails when a page
  differs from what the schemas generate. The schemas themselves are written by `retake schema
  --output Documentation/reference`, as Documentation/cli.md gives it. A hidden `retake` option that
  writes both is the alternative; the reference isn't something a project needs, so it stays out of
  the command.
- **The records aren't checked** (32): the README and Documentation/'s other pages are, but the
  records keep the JSON of their day, which a later schema needn't fit.
- **The reference's pages are one table per object** (32): the top's fields, then each definition's,
  with each field's type, default (or "required") and description, and a line for keys that go
  together (`Gives exactly one of tap, drag, …, or only hold`). An inline object, such as `build`'s
  two forms, gets a section of its own, named by its path and the key that picks it. The
  descriptions are the schemas', written for hover in an editor, so the prose stays in the README.
- **A release refuses a clone by refusing to build, not to run** (33). The plan said a release build
  "refuses to run with `RETAKE_BUTTONHEIST_PATH` set"; at run time the variable means nothing to a
  built `retake`, which reads it only through `Package.swift`, so the script refuses to build with
  it, and a build from a clone says so in `version` and every take's metadata.
- **The release's version is retake's own** (33): the tarball is named for what `retake version`
  reports, and the workflow fails when the tag names another, so releasing is a commit that sets
  `RetakeVersion.current` (`0.0.1-dev` to `0.0.1`), then its tag.
- **A pre-commit hook checks the schemas** (asked 2026-10-27): `Scripts/git-hooks/pre-commit`, on
  with `git config core.hooksPath Scripts/git-hooks`, refuses a commit touching `Sources/` or the
  schemas whose staged schemas differ from what a build of the working tree generates. It builds the
  working tree rather than the staged files, so a shared build folder stays incremental; unstaged
  changes in `Sources/` can then sway it, which it says when it fails. The reference pages aren't
  checked by it, since only the tests generate them; the test catches those.
- **The support library's aspect replaced every view's layout on iOS 17** (found on "Sam's iPad",
  iPadOS 17.7.6, 2026-10-27). It replaced `UIWindow`'s `setFrame:` and `layoutSubviews` with
  `method_setImplementation`, and on iOS 17 `UIWindow` inherits `layoutSubviews`, so that replaced
  `UIView`'s: the first navigation laid out a `UITransitionView`, asked it for its `windowScene`,
  and the app crashed. Now an inherited method is added to `UIWindow` alone, and only one of its own
  is replaced. iOS 26 overrides both, which is why the iPad Pro never showed it. Its check is the
  example's integration test, on an iOS 17 device, since the library can't run on the Mac.
- **The example names its Library back button by its trait** (34): on the 6th-generation iPad's
  narrower screen, the sidebar's "Library" header is on screen beside it, so `tap "Library"` matched
  both. `"traits": ["button"]` tells them apart, as the README says traits are for. With that and
  the support library's fix, the integration test passed on "Sam's iPad" (`ipad2`): install to cut
  in 52 s.
- **`check` passed an app it couldn't read** (found 2026-10-27, putting it in Puzz's archive phase).
  Every read in it swallowed its error: a `Frameworks` folder it couldn't list, an unreadable
  `Info.plist`, `nm` failing on an executable. Each came back as "nothing here". In a build phase
  with Xcode's script sandbox on, declaring only the `.app` as an input doesn't let the phase read
  inside it, so a planted `TheInsideJob.framework` passed. Now any of those fails (1), naming the
  path; a folder that isn't there is still clear. `embed` shares the detector, and fails the same
  way on an app it can't read. Checked in a sandboxed phase on a copy of the example: with the app,
  its `Info.plist`, executable and `Frameworks` declared, `check` found a planted framework and
  passed the clean app; with only the `.app` declared, it fails rather than passing.

### Obviated

Made moot by a later change, kept for the record.

- **A pre-release reads its release's schema** (3). `0.0.1-dev` reads files whose `"$schema"` names
  `0.0.1` without a warning, and `init` will write `0.0.1`'s URL, since pre-releases have no
  published schemas of their own. **Obviated:** `init` names no schema since Retake stopped adding
  `"$schema"` ("Retake never adds `"$schema"`"), so only the reading half remains, which matters only once schemas are
  published.
- **`inspect` is given as `true` or `{}`** (6), since it takes no options yet; `{}` leaves room for
  some, such as limiting it to a part of the screen. **Obviated:** the `inspect` step went when
  `compose` replaced `inspect` (21c).
- **Overrides can't give `devices`, `takes` or `intent`** (7; since, `intent` can be given per
  device type, and edits name no takes), which are per edit, or already per device type; any other
  field, at the top or inside a clip, caption or any object, can be. An override inside an override,
  such as `"ipad": { "iphone": … }`, is an error. **Obviated:** `intent` can be given per device
  type, and edits name no takes, which leaves `devices`, which says which types there are.
- **`validate` without `--offline` notes that takes aren't checked yet** (8): until anchors resolve
  against takes (24), it runs the offline checks and says so, rather than failing. Since 24 it
  checks them. **Obviated:** since 24, `validate` checks anchors against the takes.
- **Recognising an unregistered device is by `xcodebuild`'s message text** (16), which
  `isUnregisteredDevice` matches on phrases such as "doesn't include the currently selected device";
  the phrases are from Xcode's known messages, not yet seen from a real unregistered device here.
  **Obviated:** the unregistered-device check is below the bar for v0.0.1, since every device
  recorded on is on the team.
- **`rehearse` keeps the app's console in a temporary folder** (18), not `RetakeOutput/logs/`, since
  Documentation/cli.md says rehearsing "writes nothing". The folder is left for the system to clear;
  the error for a launch that fails still quotes the console's last lines. **Obviated:** `rehearse`
  became `record --dry-run` (21b); where every launch's console goes is the later follow-up,
  "`record` keeps a launch's console log in a temporary folder".
- **`--from` skips the holds of the steps before it, not the setup's** (18). Since dropped from the
  contract (review of 2026-10-27): a step can need the one before's hold. Documentation/cli.md says
  the steps before `--from` play "without their holds"; setup steps aren't numbered among the steps,
  and their holds let the app settle before the first step, so they keep them. **Obviated:**
  `--from` is gone.
- **The device's orientation isn't restored after a rehearsal** (18). It's left however the scene's
  last step left it. The next launch turns it to its scene's `orientation` anyway, so a take never
  starts turned; restoring it would need its orientation read before launch, which `devicectl device
  orientation` can do. **Obviated:** every launch turns the device to its scene's orientation, and
  since 2026-11-02 a take recorded from before launch is turned before recording starts, so there's
  nothing to restore.
- **The example's `reorder` scene is iPad only** (18; since, the iPhone has its own, dragging the
  last note on its screen). It drags a row by its iPad screen points and
  turns the iPad, and there's no iPhone here to read the iPhone's points from, so `scenes/iphone/`
  has no `reorder` yet. An edit that cut it couldn't name both device types until it has one.
  `SceneFileTests` now checks that each type has at least `create-note` and `first-launch`, rather
  than exactly those.
  **Obviated:** the iPhone has its own `reorder`, and each type's edit cuts it.
- **`inspect` launches the app upright** (19). It takes no scene, so it launches as a scene with no
  `orientation` does, turning the device to portrait first, so a printout's points match a portrait
  scene's. While watching, the device can be turned by hand (or with `devicectl`) and the new layout
  is printed. An `--orientation` option could launch it turned instead. **Obviated:** `compose`
  replaced `inspect` (21c), launching on its scene's orientation.
- **`inspect` shows the screen once it has settled** (19), not at the first look: it looks every
  0.25 s until two looks agree, for up to 3 s, then shows what it has. Found on the iPad: the first
  look after launch caught the app still settling (a header's traits and two elements' order changed
  a moment later), which `--watch` then printed as a change that wasn't one. **Obviated:** carried
  into `compose`, which shows the screen once two readings agree.
- **`--watch` prints a change once it has held for two looks** (19), a quarter second apart, and
  never a screen mid-animation. A screen that never stops changing, such as a running timer or a
  looping animation in an element's value or frame, is never printed again while it changes;
  comparing only labels, or only some fields, would let it through at the cost of missing real
  changes. Changes are printed whole, not as a difference from the last. **Obviated:** `--watch`
  went with `inspect` (21c).
- **`--watch` ends with Control-C, exiting 0** (19). Documentation/cli.md says it prints "until
  stopped"; Control-C is caught while watching, so the app is still launched once more to delete the
  take's copy of its data, and "Stopped." is printed. A second Control-C during that cleanup is
  ignored. Each screen is flushed as it's printed, so `--watch` works through a pipe. **Obviated:**
  `--watch` went with `inspect` (21c); Control-C ends `compose` as `quit` does.
- **`inspect` lists only what's on screen** (19). It reads The Button Heist's current interface
  (`captureInterface()` with its default, `.current`), without scrolling to discover elements
  further down a list, so an element scrolled off isn't listed. A step can still target one, since
  The Button Heist scrolls to it when acting. **Obviated:** true of `compose` now, whose `inspect`
  action reads the same current interface.
- **Each element is printed with its value and identifier too** (19). Documentation/cli.md says
  `inspect` prints "each element's label, traits, frame and activation point"; a step can name an
  element by its `value` (a text field's placeholder) or `identifier` as well, so they're printed
  when an element has them: `(no label) value "Title" textEntry frame (485.5, 136, 586.5×28) at
  (778.75, 150)`. Documentation/cli.md could say so. **Obviated:** Documentation/cli.md's `compose`
  now lists each element's label, value, identifier, hint, traits, frame and activation point.
- **Preview sizes are provisional** (25): 886×1920 for iPhone and 1200×1600 for iPad, at 30 frames a
  second, as the pipeline Retake grew from shipped them (`PreviewSpec`). The plan already has App
  Store Connect's current specifications looked up before the export lands (28); they're corrected
  there if they differ. **Obviated:** checked against App Store Connect's specifications in 28,
  below; they stand.
- **The example's tour was lengthened to make a preview** (34). As it was, it cut 9.5 s on the iPad,
  short of App Store Connect's 15, so a full `cut` refused it. It now starts on the welcome screen
  arriving and ends its first clip once the library shows, plays the share at its own speed, and
  adds a fourth clip, `filed`, back to the library with the new note in it: 16.2 s on Sam's iPad
  (2), cut in full (H.264 High, 1200×1600, AAC). The iPhone's length is still to be seen, waiting on
  its takes, which the sheet-tap follow-up holds up. **Obviated:** the iPhone's takes came, and its
  tour cuts at 22.6 s.
- **The integration test runs `retake` itself** (34; since, without `conform`, which `cut` took
  over), as a person would: `install` from the example, then `validate --offline`, `record --for
  tour`, `conform`, `validate`, `cut` on a copy of its `Retake/` folder (since `conform` rewrites
  the edit) with an output directory of its own, then `info --json` and `status --json` on the
  result. It finds the `retake` built beside the test bundles, or `RETAKE_TEST_BINARY`. The same
  flow, by hand, ran on Sam's iPad (2) before the user moved device checks to "Sam's iPad" (`ipad2`,
  a 6th-generation iPad on iPadOS 17); the test itself is to run there once it's connected by USB.
  **Obviated:** it ran on "Sam's iPad" (`ipad2`), passing, as the entry on the Library back button
  says.
- **The README's quick start conforms before it cuts** (34, contract; since, `cut` prepares the
  edit itself, so the step is gone): a cut needs the edit's pins,
  and `conform` is what makes them, so the quick start was missing a step. The README now points at
  the example as the way to start, with its signing set up first.
  **Obviated:** `cut` prepares the edit itself, so there's no `conform` step to put first.
